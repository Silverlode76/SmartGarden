## Überblick: Vollständige End-to-End-Pipeline

Der erste Prototyp hatte bereits eine **komplette IoT-Pipeline** von der Hardware bis zur App:

```
╔══════════════════════╗    LoRa 433 MHz    ╔═══════════════════════╗    WiFi    ╔═══════════════╗    Flutter
║     SLAVE NODE       ║ ─────────────────► ║   MASTER / GATEWAY    ║ ─────────► ║  Google Cloud ║ ◄──────────
║   (Garten / Außen)   ║                    ║   (Haus / USB-Strom)  ║            ║  (Firebase?)  ║    App
╠══════════════════════╣                    ╠═══════════════════════╣            ╚═══════════════╝
║ STM32F103C8T6        ║                    ║ STM32F103C8T6         ║
║ SX1278 (433 MHz)     ║                    ║ SX1278 (433 MHz)      ║
║ GY-BME280            ║                    ║ ESP8266 WiFi Module   ║
║ LiPo 110mAh + Solar  ║                    ║ USB-Stromversorgung   ║
╚══════════════════════╝                    ╚═══════════════════════╝
```

> **Wichtige Korrektur:** Das Master-Modul verwendete einen **ESP8266** (nicht ESP32).  
> Dies ist aus dem Fritzing-Schaltplan des Masters ersichtlich (Bauteil U1: „ESP8266 WiFi Module").

---

## Master-Modul: Komponenten (aus Fritzing-Schaltplan)

| Ref. | Bauteil | Typ | Funktion |
|------|---------|-----|----------|
| M1 | STM32F103C8T6 „Blue Pill" | Mikrocontroller | LoRa-SPI-Handler; Paket-Parser; UART-Bridge zu ESP8266 |
| A1 | LoRa SX1278 Module | LoRa Transceiver 433 MHz | Empfängt Pakete vom Slave per LoRa |
| U1 | ESP8266 WiFi Module | WiFi-Modul (ESP-01 Formfaktor) | AT-Kommando-Modem oder eigene Firmware; WiFi → Google Cloud |

**Stromversorgung:** Permanent über USB (kein Akkubetrieb, kein Solar — Gateway im Haus)

## Master-Schaltplan: Pin-Belegung (aus Fritzing)

### STM32F103C8T6 → SX1278 (SPI)

| SX1278 Pin | Signal | STM32 Pin (SPI1) |
|------------|--------|-----------------|
| MISO (7) | SPI MISO | PA6 |
| MOSI (8) | SPI MOSI | PA7 |
| SCK (9) | SPI Clock | PA5 |
| NSS (10) | Chip Select | PA4 |
| DIO0 (11) | RxDone / TxDone IRQ | GPIO (z.B. PA0) |
| DIO1 (2) | RxTimeout | GPIO |
| REST (12) | Reset | GPIO |
| VCC (5) | 3,3V | 3V3 |
| GND (1,12) | GND | GND |

### STM32F103C8T6 → ESP8266 (UART)

| ESP8266 Pin | Signal | STM32 Pin |
|-------------|--------|-----------|
| TXD (8) | ESP → STM32 | USART RX (z.B. PA10) |
| RXD (9) | STM32 → ESP | USART TX (z.B. PA9) |
| CH_PD (6) | Chip Enable | 3V3 (muss HIGH sein) |
| RSTn (4) | Reset | GPIO oder 3V3 |
| VCC (2) | 3,3V | 3V3 |
| GND (1, 7) | GND | GND |

### Debug-Port (aus Slave-Schaltplan bekannt, vermutlich auch im Master)

| Signal | STM32 Pin | Beschreibung |
|--------|-----------|-------------|
| UART TX | PB10 | Debug-Ausgabe auf PC |
| UART RX | PB11 | Debug-Eingang |

## Interner Datenfluss im Master

```
[SX1278 LoRa Modul]  ←── 433 MHz LoRa Funk ←── Slave Node
        │
        │ SPI (MOSI/MISO/SCK/NSS + DIO0 IRQ)
        ▼
[STM32F103C8T6]
  - SX1278 SPI-Stack (IRQ auf DIO0)
  - LoRa-Paket parsen (proprietäres Protokoll)
  - Payload extrahieren: Temperatur, Luftfeuchte, Luftdruck
        │
        │ UART (AT-Kommandos oder direktes Protokoll)
        ▼
[ESP8266 WiFi Module]
  - WiFi-Verbindung zum Router
  - HTTP/HTTPS → Google Cloud
  - Alternativ: MQTT-Broker
        │
        │ Internet
        ▼
[Google Cloud]
  - Firebase Realtime Database oder Firestore
  - Messwerte gespeichert mit Timestamp
        │
        │ SDK / REST API
        ▼
[Flutter App]
  - Temperaturen, Luftfeuchtigkeit, Luftdruck anzeigen
  - Kommandos senden (Steuerung)
```

## Erkenntnisse aus der Dual-MCU-Master-Architektur

| Beobachtung | Konsequenz für v0.1+ |
|-------------|---------------------|
| **ESP8266 als AT-Modem funktioniert** — aber aufwändig (AT-Kommandos, Timing) | ESP32 hat WiFi integriert + bessere Libs → direkt nutzbar ohne Brücken-MCU |
| **Dual-MCU (STM32+ESP8266)** für Gateway = doppelte Firmware-Basis | TTN übernimmt die Gateway-Funktion komplett → kein eigener Gateway-Bau nötig |
| **Proprietäres LoRa-Protokoll** muss selbst gebaut und gewartet werden | LoRaWAN (standardisiert) auf TTN → Community-Gateways, kein eigenes Protokoll |
| **SX1278 = 433 MHz** nicht TTN/EU868-kompatibel | SX1276 in TTGO → 868 MHz EU-Standard |
| **Google Cloud + Flutter** als Stack hat funktioniert | Konzept für SmartGarden v1.0 übernommen: Cloud-Backend + Flutter-App |
| **Gateway im Haus** = Reichweitenabhängigkeit, Single Point of Failure | TTN Community-Gateways = für Pilotphase kein eigener Gateway nötig |

## Systemvergleich: v0.0 → v0.1+ → v1.0

```
v0.0 (2025) — Proprietär / Selbstgebaut:
  STM32+SX1278 ──433MHz──► STM32+SX1278+ESP8266 ──WiFi──► Google Cloud ──► Flutter
  Eigenes Protokoll | Eigener Gateway | Bewährt: Cloud+Flutter-Stack

v0.1 (2026) — LoRaWAN / Standard:
  TTGO LoRa32 ──EU868 LoRaWAN──► TTN Gateway ──Internet──► TTN ──► Backend ──► Flutter
  Standard-Stack | Community-Gateways | Cloud-Agnostisch

v1.0 (2027) — Produkt:
  Custom PCB ──EU868 LoRaWAN──► SmartGarden Gateway ──Internet──► SmartGarden Cloud ──► Flutter
  Eigene Hardware | Eigener Gateway (Vereins-Modell) | Eigenes Backend
```

## Bedeutung für das Produkt

Die v0.0-Architektur war ein wertvoller **Proof of Concept für die gesamte Pipeline:**

- ✅ **Hardware → LoRa → Gateway:** STM32 + SX1278 LoRa-Kommunikation funktioniert
- ✅ **BME280:** Liefert brauchbare Außenmesswerte (Temp / Feuchte / Luftdruck)
- ✅ **Gateway → Cloud:** ESP8266 WiFi → Google Cloud funktioniert
- ✅ **Cloud → App:** Google Cloud + Flutter App — vollständige Kette bewiesen
- ✅ **Solarbetrieb:** Konzept grundsätzlich möglich (Dimensionierung noch falsch)
- ❌ **433 MHz:** Kein LoRaWAN EU-Standard → kein TTN möglich
- ❌ **Proprietäres Protokoll:** Skaliert nicht auf Mehrbenutzer/Vereins-Betrieb
- ❌ **Eigener Gateway:** Single Point of Failure, manuelle Wartung
- ❌ **Akku 110mAh + schwache Solar:** Energiebudget für Outdoor-Dauerbetrieb unzureichend

→ **Das Konzept war richtig. Die Implementierung wurde durch LoRaWAN/TTN standardisiert.**
