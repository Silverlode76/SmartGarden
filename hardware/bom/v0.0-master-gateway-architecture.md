## Überblick

Der erste Prototyp war keine einfache Bastelschaltung — er war eine
**vollständige IoT-Architektur** mit professionellen Komponenten auf jeder Schicht:

```
┌─────────────────────┐                ┌─────────────────────────┐
│  Slave Node "uuid1" │                │                         │
│  STM32 + SX1278     │◄──────────────►│                         │  MQTT   ┌────────────────┐
└─────────────────────┘   LoRa 433 MHz │   GATEWAY "uuid3"       │◄───────►│                │  MQTT
                                        │   Raspberry Pi          │         │ Google Cloud   │◄──────► Flutter App
┌─────────────────────┐   LoRa 433 MHz │   SX1302 Konzentrator   │◄───────►│  IoT Core      │
│  Slave Node "uuid2" │◄──────────────►│                         │         │  + Firebase    │
│  STM32 + SX1278     │                │                         │         └────────────────┘
└─────────────────────┘                └─────────────────────────┘
       Slave Nodes                            Gateway                         Cloud + App
     (akku-/solar-betrieben)          (permanent, USB/Netz)
```

## Schicht 1 — Slave Nodes (Außen, Akkubetrieb)

| Parameter | Wert |
|-----------|------|
| MCU | STM32F103C8T6 „Blue Pill" |
| LoRa | SX1278 Breakout-Modul (433 MHz) |
| Sensor | GY-BME280 (Temperatur / Luftfeuchte / Luftdruck) |
| Energie | LiPo 110mAh + Solar (Mini-360 → TP4056) |
| Adressierung | UUID-basiert (z.B. „uuid1", „uuid2") |
| Protokoll | Proprietäres LoRa-Protokoll auf 433 MHz (bidirektional) |
| Anzahl | 2 Nodes im Prototyp |

## Schicht 2 — Gateway (Haus / permanent)

### Hardware

| Komponente | Details |
|------------|---------|
| **Raspberry Pi** | Gateway-Computer (Modell unbekannt, USB-Stromversorgung) |
| **SX1302** | Semtech 8-Kanal-LoRa-Konzentrator-IC (kein einfaches Breakout!) |
| **UUID** | „uuid3" — Gateway hat eigene Identität im Netz |

> **SX1302 — kein Breakout-Modul:** Der SX1302 ist der Chip aus professionellen  
> LoRaWAN-Gateways (z.B. RAK WisGate, Dragino). Er kann **8 LoRa-Kanäle gleichzeitig**  
> empfangen. Für den Raspberry Pi gibt es SX1302-HATs (z.B. Waveshare SX1302 LoRaWAN-HAT).

### Verbindung zur Cloud: MQTT

```
Raspberry Pi (SX1302)  ←──MQTT──►  Google Cloud IoT Core
```

- **Protokoll:** MQTT (bidirektional — Uplink + Downlink)
- **Broker:** Google Cloud IoT Core (managed MQTT broker)
- **Gateway-UUID:** „uuid3" identifiziert den Gateway im Cloud-System

### Zweites Gateway-Design: STM32 + ESP8266

Neben dem Raspberry Pi existierte ein einfacheres Gateway-Design auf Basis  
des Fritzing-Schaltplans:

| Komponente | Funktion |
|------------|----------|
| STM32F103C8T6 | LoRa-SPI-Handler (SX1278), UART-Bridge |
| SX1278 | LoRa 433 MHz Empfänger |
| ESP8266 WiFi Module | WiFi-Konnektivität → Firebase |

→ Dieses Design wurde möglicherweise als einfacherer Prototyp vor dem Raspberry Pi gebaut.

## Schicht 3 — Cloud: Google Cloud IoT Core + Firebase

| Dienst | Funktion |
|--------|----------|
| **Google Cloud IoT Core** | Managed MQTT-Broker für IoT-Geräte; Device Registry mit UUIDs |
| **Firebase** | Realtime Database / Firestore für Messwert-Speicherung |

Verbindungen:
- Gateway → Cloud IoT Core: MQTT (Uplink-Pakete + Downlink-Kommandos)
- Cloud IoT Core → Firebase: Interne Weiterleitung / Cloud Functions
- Cloud → Flutter App: MQTT direkt oder Firebase SDK

---

## Schicht 4 — App: Flutter

- Empfängt Sensor-Daten via **MQTT** von Google Cloud IoT Core
- Zeigt Temperatur, Luftfeuchte, Luftdruck der Slave Nodes
- Kann Kommandos senden (Downlink via MQTT → Cloud → Gateway → Node)
- **Stack:** Flutter (Dart) → MQTT-Client-Library → Cloud IoT Core

## Boot-Sequenz: STM32 + ESP8266 Gateway

Dokumentiert in Flussdiagramm (Architekturbild 2):

```
STM32                           ESP8266
  │                                │
  │──── Init ESP8266 ─────────────►│
  │                             Access AP (WiFi)
  │                                │
  │                             AP_OK?
  │                           no ──┤──► retry (loop)
  │                           yes  │
  │                             Connect FB (Firebase)
  │                                │
  │                             FB_OK?
  │                           no ──┤──► retry (loop)
  │                           yes  │
  │                             Confirm Connect to FB
  │◄─── Bestätigung ───────────────│
  │
Init LoRa (SX1278)
  │
[System betriebsbereit]
```

**Design-Entscheidung der Sequenz:**
- LoRa wird **erst nach** gesicherter Cloud-Verbindung initialisiert
- → Kein Datenverlust: Alle LoRa-Pakete die nach Init ankommen können sofort weitergeleitet werden
- → Wenn WiFi/Firebase nicht verfügbar → System wartet (retries), startet LoRa nicht

## UUID-Adressierungsschema

Jedes Gerät im System hat eine eindeutige UUID:

| UUID | Gerät | Typ |
|------|-------|-----|
| uuid1 | Slave Node 1 | STM32 + SX1278 |
| uuid2 | Slave Node 2 | STM32 + SX1278 |
| uuid3 | Gateway | Raspberry Pi + SX1302 |

**Bidirektionale LoRa-Kommunikation:** Die blauen Pfeile im Architekturdiagramm  
zeigen **beide Richtungen** — Uplink (Node → Gateway) und Downlink (Gateway → Node).  
Downlink ermöglicht z.B. Konfigurationsänderungen oder Aktor-Steuerung.

### v0.0 war konzeptionell vollständig richtig

> **Die v0.0-Architektur ist im Kern identisch mit TTN:**  
> Nodes → LoRa → Gateway (SX1302) → MQTT → Cloud → App  
>  
> TTN macht genau das — nur mit standardisiertem LoRaWAN-Protokoll  
> statt proprietärem 433 MHz-Protokoll.  
>  
> Der Wechsel zu TTN/LoRaWAN in v0.1 war **kein Paradigmenwechsel**,  
> sondern eine **Standardisierung** einer bereits bewiesenen Architektur.

### Erkenntnisse → Änderungen in v0.1

| v0.0-Erkenntnis | Lösung v0.1+ |
|-----------------|-------------|
| 433 MHz: kein EU-Standard, kein TTN | EU868 LoRaWAN → TTN-kompatibel |
| Eigener MQTT-Broker (Cloud IoT Core) zu pflegen | TTN als managed LoRaWAN-Netz → kein eigener Broker |
| Eigenes Device-Management (UUID) | LoRaWAN-Standard (DevEUI, AppEUI, AppKey) |
| Raspberry Pi + SX1302 = teurer eigener Gateway | TTN Community-Gateways für Pilotphase kostenlos |
| Proprietäres Protokoll = kein Interop | LoRaWAN-Standard = sofortige Interoperabilität |
| SX1278 (433 MHz) in Nodes | SX1276/SX1262 (EU868) in TTGO / Custom PCB |
| Firebase direkt vom Gateway | Backend entkoppelt: TTN → Webhooks → eigenes Backend |
