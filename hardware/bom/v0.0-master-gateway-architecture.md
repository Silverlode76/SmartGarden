## Überblick: Zweistufiges proprietäres System

Der erste Prototyp bestand aus **zwei eigenständigen Modulen** mit einem
selbst entwickelten (proprietären) LoRa-Protokoll auf 433 MHz:

```
╔══════════════════════════════╗         LoRa 433 MHz         ╔══════════════════════════════╗
║       SLAVE NODE             ║  ─────────────────────────►  ║       MASTER / GATEWAY       ║
║  (Garten / Außen)            ║                               ║  (Haus / Innen)              ║
╠══════════════════════════════╣                               ╠══════════════════════════════╣
║ STM32F103C8T6 "Blue Pill"    ║                               ║ ESP32                        ║
║ SX1278 LoRa (433 MHz)        ║                               ║ STM32 (LoRa-Handler)         ║
║ GY-BME280 (T/H/P)            ║                               ║ SX (LoRa Transceiver)        ║
║ LiPo 110mAh                  ║                               ║ WiFi → Cloud / PC            ║
║ Solar + TP4056                ║                               ║                              ║
╚══════════════════════════════╝                               ╚══════════════════════════════╝
        Stückliste: v0.0-stm32-prototype-bom.md                      Stückliste: s.u.
```

## Master / Gateway (v0.0)

> **Hinweis:** Kein Fritzing-Schaltplan vorhanden. Beschreibung aus der Erinnerung.
> Falls ein Schaltplan vorliegt → bitte hier verlinken.

### Komponenten

| Komponente | Funktion |
|------------|----------|
| **ESP32** (Dev-Board) | WiFi-Konnektivität, Cloud-Upload, Hauptlogik |
| **STM32** (Blue Pill o.ä.) | LoRa-Empfang und Paket-Parsing (dedizierter LoRa-Handler) |
| **SX-Modul** (SX1278 kompatibel) | LoRa-Transceiver, 433 MHz, empfängt Slave-Pakete |

### Interne Kommunikation im Master

```
[SX1278 LoRa Modul]
        │ SPI
  [STM32 (LoRa Handler)]
        │ UART / Serial
    [ESP32]
        │ WiFi
    [Cloud / PC / App]
```

**Warum zwei MCUs im Master?**
- Der STM32 übernimmt das zeitkritische SPI-Timing des SX1278 (LoRa-Stack)
- Der ESP32 übernimmt die WiFi-Verbindung und Cloud-Kommunikation
- Beide MCUs kommunizieren über UART miteinander
- → Trennung von Echtzeit-LoRa und netzwerk-asynchronem Upload

### Betriebsablauf

```
1. Slave sendet LoRa-Paket (Messwerte) → 433 MHz
2. SX1278 im Master empfängt Paket
3. STM32 liest SX1278 per SPI, parst Payload
4. STM32 → UART → ESP32: weiterleiten der Messwerte
5. ESP32 baut WiFi-Verbindung auf
6. ESP32 sendet Daten an Cloud / PC-Anwendung
```

## Erkenntnisse aus der Dual-MCU-Master-Architektur

| Beobachtung | Konsequenz für v0.1+ |
|-------------|---------------------|
| Zwei MCUs für eine Gateway-Funktion = doppelter Aufwand (Firmware, Verdrahtung) | In v0.1: **TTN übernimmt die Gateway-Funktion** komplett — kein eigener Gateway-Bau nötig |
| Proprietäres LoRa-Protokoll muss selbst implementiert und gewartet werden | LoRaWAN (standardisiert) auf TTN → Community-Gateways nutzbar |
| SX1278 (433 MHz) nicht TTN-kompatibel | SX1276 in TTGO LoRa32 → EU868 → TTN-kompatibel |
| ESP32 + WiFi als Connectivity-Layer | Konzept bleibt richtig — in v0.1 übernimmt TTN/Cloud die Connectivity |
| Gateway im Haus = Reichweitenabhängigkeit | TTN Community-Gateways = kein eigener Gateway für Pilotphase nötig |

## Systemvergleich: v0.0 (proprietär) vs. v0.1+ (LoRaWAN)

```
v0.0 — Proprietär (selbst gebaut):
  [Slave: STM32 + SX1278] ──433MHz──► [Master: STM32+ESP32+SX] ──WiFi──► Cloud
  Nachteil: 2× eigene Firmware, nur ein Gateway, kein Standard

v0.1+ — LoRaWAN / TTN:
  [Node: TTGO LoRa32] ──EU868 LoRaWAN──► [TTN Gateway (community)] ──Internet──► TTN
  Vorteil: Standard-Stack, Community-Gateways, keine eigene Gateway-Firmware
```

## Bedeutung für das Produkt

Die v0.0-Architektur war ein wertvoller **Machbarkeitsnachweis**:

- ✅ Bewiesen: STM32 + LoRa kann Sensordaten drahtlos übertragen
- ✅ Bewiesen: BME280 liefert brauchbare Außenmesswerte
- ✅ Bewiesen: Solarbetrieb grundsätzlich möglich
- ✅ Bewiesen: Dual-MCU-Architektur (LoRa-Handler + WiFi-Gateway) funktioniert konzeptionell
- ❌ Erkannt: Proprietäres Protokoll skaliert nicht auf Vereins-/Mehrmandanten-Betrieb
- ❌ Erkannt: Eigener Gateway = Single Point of Failure
- ❌ Erkannt: 433 MHz kein EU-LoRaWAN-Standard

→ **Wechsel zu LoRaWAN + TTN für v0.1** war die direkte Konsequenz aus diesen Erkenntnissen.
